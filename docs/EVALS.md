## Live-run notes

- Groq free tier returned HTTP 429 (tokens-per-minute) on most requests; the client retried once honouring `Retry-After`, which is why guest runs took 2–3 minutes. Each request re-sends the whole transcript, so spacing requests 2.5 s apart is not enough — expect ~10–15 s between model calls for a 429-free run.
- Mid-run provider fallback to Gemini is **not viable** with Gemini 3.x function calling: Gemini rejects a transcript that contains another model's tool calls (`thought_signature` missing). A fallback that restarts the run from scratch on the fallback model would work; this harness records the failure rather than hiding it.
- A live guest run takes about 2 minutes (8 or so model calls with reasoning, plus retries); the deterministic engine answers in well under a second.

## How to read this

- *Verified correct* for the guest means the SERVER's re-verification of what the guest proposed matches the ground truth (and for Scenario A, the checkout 14:05 deploy is not among the supported suspects). The guest never sees the ground truth; only the scorer does.
- *Ruled-out correct* counts only if the server STORED the deployment as a rejected hypothesis with failed checks. How: `proposed_and_rejected` (the guest blamed it, the verifier rejected it) or `rejected_by_server_check` (the guest never named it; the server checked the whole dependency path anyway).
- *What to expect when recording:* a live guest run takes about 2 minutes on the Groq free tier (8 or so model calls with reasoning, plus 2.5 s spacing in evals); the deterministic engine answers in well under a second.
- *Fallbacks* count model switches (Groq → Gemini) observed in live mode; the deterministic template fallback applies to narratives only, which the guest does not write.
- Offline mode replays recorded tool-call sequences through a fake chat model; Scenario A replays the real live run. It exercises the MCP server, the catalog validation and the server-side verifier, not the LLM.
